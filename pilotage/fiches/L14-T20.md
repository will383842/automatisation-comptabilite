## Contexte
Spec 14, `02` partie A, règle 4, et décision D21 de Will (« le mois reste MODIFIABLE, avec une trace de chaque changement ») : si le client change le mois de rattachement d'une pièce, le montant et l'échéance sont recalculés ; la modification et l'ancienne valeur sont au journal. Test D4 : pièce déplacée d'octobre à novembre : montants des deux périodes recalculés, 1 ligne de journal avec l'ancien et le nouveau mois.

## À faire
1. `packages/noyau/src/tva/rattachement.ts` (classe locale `ErreurRattachement`) :
   - `Rattachement { pieceId: string; mois: string /* AAAA-MM */ }` ; `LigneJournalRattachement { pieceId; ancienMois; nouveauMois; par; le }` ;
   - `deplacerPiece(rattachements, { pieceId; nouveauMois; par; le }, periodesDeposees: readonly string[])` → `{ rattachements; journal: LigneJournalRattachement; periodesARecalculer: readonly [string, string] }` ; la liste reçue n'est pas modifiée ; même mois = refus `mois_identique` (aucune ligne de journal vide) ; pièce inconnue = refus ; mois de départ ou d'arrivée dans `periodesDeposees` = refus `periode_deposee` (une période déposée ne se modifie pas : on régularise ailleurs).
2. Tests nommés : `d4-octobre-vers-novembre-une-ligne-de-journal`, `d4-deux-periodes-a-recalculer`, `entree-non-modifiee`, `meme-mois-refuse`, `periode-deposee-refusee`, `piece-inconnue-refusee`.

## Hors périmètre
Pas de recalcul des montants ici (lot 03, totaux) : la fonction rend les périodes à recalculer. Pas de stockage du journal.

## Pièges
Règles du noyau comme L14-T02. Cas limites exigés : mois mal formé (« 2026-13 », « 2026-1 »), `par` vide, `le` mal formé, deux rattachements pour la même pièce dans l'entrée (refus `rattachement_ambigu`), liste vide.
